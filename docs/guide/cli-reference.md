# Command reference

Every command and option, as `liftoff <command> --help` prints them. This page is generated by
`node scripts/cli-reference.ts` in `packages/liftoff`; do not edit it by hand.

## Options every command takes

| option | what |
| --- | --- |
| `-C, --project-dir <DIR>` | the project folder, which holds `liftoff.toml` (default: the current folder) |
| `-e, --environment <NAME>` | the environment to work on |
| `--output-type <TYPE>` | `text` (default) or `json`: one JSON object on stdout, progress on stderr |
| `--placeholder <NAME=VALUE>` | a value for `${NAME}` in the scripts, for this run; repeatable |
| `-h, --help` | the command's help |
| `-V, --version` | the program's version |

Flyway-style options (`-url=…`, `-user=…`, `-locations=filesystem:…`) are accepted too; see
[Moving from Flyway](flyway.md#flyway-style-arguments). Exit codes are listed in
[Deploying](deploying.md#exit-codes).

## Projects and settings

### init

Create liftoff.toml, migrations/ and schema-model/ in the project folder

```
Usage: liftoff init [OPTIONS]

Options:
      --name <NAME>                  Project name (default: the folder name)
      --engine <ENGINE>              postgresql or sqlserver [default: postgresql]
      --from-flyway                  Convert the folder's flyway.toml or flyway.conf instead of starting empty (the originals stay)
      --flyway-config <FILE>         With --from-flyway: which Flyway config file, when the folder has more than one
      --include <NAME>               With --from-flyway: only this environment (repeatable; default: all)
      --role <NAME=ROLE>             With --from-flyway: the role for an environment, e.g. live=prod (repeatable)
      --preview                      With --from-flyway: show what would be converted, and write nothing
      --sample                       Start from a small sample shop project (an empty folder only)
```

### settings

Show every project setting and environment as written in the files (passwords left out). With --save, apply changes read as JSON from stdin

```
Usage: liftoff settings [OPTIONS]

Options:
      --save                         Read {"project": {...}, "environments": [...], "remove": [...]} from stdin and save it; passwords go to the keychain or liftoff.user.toml
```

### project

Show the project and its environments: name, role and engine (no connection details)

```
Usage: liftoff project [OPTIONS]
```

### test-connection

Check that an environment is reachable

```
Usage: liftoff test-connection [OPTIONS]
```

### create-scratch

Create an empty scratch database next to the dev database and save it as an environment

```
Usage: liftoff create-scratch [OPTIONS]

Options:
      --from <FROM>                  Dev environment (default: the first with role "dev")
      --name <NAME>                  Name for the new environment [default: scratch]
```

## Writing migrations

### diff

Compare the dev database (or the schema model) with what the migrations build

```
Usage: liftoff diff [OPTIONS]

Options:
      --from <FROM>                  dev (the dev database) or model (the schema-model folder; no dev database needed) [default: dev]
      --source <SOURCE>              Dev environment (default: the first with role "dev")
      --scratch <SCRATCH>            Scratch environment rebuilt for the comparison (default: the first with role "scratch")
```

### generate

Write the next migration from the differences

```
Usage: liftoff generate [OPTIONS]

Options:
      --description <DESCRIPTION>    What the migration does (required)
      --from <FROM>                  dev (the dev database) or model (the schema-model folder; no dev database needed) [default: dev]
      --source <SOURCE>              Dev environment (default: the first with role "dev")
      --scratch <SCRATCH>            Scratch environment (default: the first with role "scratch")
      --skip-destructive             Leave out changes that may lose data (dropped tables or columns, type changes)
      --dry-run                      Print the script instead of writing it
      --record-on-dev                Also record the new script as applied on the dev database, which has the change (from model: when dev has it, checked)
      --undo                         Also write the matching undo script (U…)
```

### add

Create the next migration file to write by hand

```
Usage: liftoff add [OPTIONS]

Options:
      --description <DESCRIPTION>    What the script does (required)
      --repeatable                   A repeatable script (R__), run again whenever it changes
      --from-file <FILE>             Read the SQL from this file instead of starting empty
```

### capture

Write the whole schema of an existing database as the next migration

```
Usage: liftoff capture [OPTIONS]

Options:
      --description <DESCRIPTION>    Description in the file name [default: existing schema]
      --dry-run                      Print the script instead of writing it
      --as-baseline-script           Write a baseline script (B…) that empty databases start from, instead of a V script
```

### model

Bring the schema-model folder up to date with dev: one file per object. With --check, build the folder on the scratch database instead

```
Usage: liftoff model [OPTIONS]

Options:
      --source <SOURCE>              Dev environment (default: the first with role "dev")
      --status                       List what differs instead of writing
      --path <FILE>                  Only this object file, e.g. tables/public.orders.sql (repeatable)
      --check                        Check the schema model builds (on the scratch database); exits 12 naming each file that does not
      --scratch <SCRATCH>            Scratch environment for --check (default: the first with role "scratch")
```

## Deploying

### info

List every migration and its state on the environment

```
Usage: liftoff info [OPTIONS]
```

### migrate

Run pending migrations

```
Usage: liftoff migrate [OPTIONS]

Options:
      --out-of-order                 Also run scripts older than the latest applied version
      --target <TARGET>              Stop after this version
      --accept-differences           A database with objects that differ from the baseline script: record the baseline anyway (the differences show up as drift)
      --scratch <SCRATCH>            Scratch environment to check a database with objects against the baseline script (default: the one with role "scratch")
      --only <SCRIPT>                Run only this script and nothing else: a version (5, 1.2), a file name, or a repeatable script's name (repeatable). Older scripts may be picked
      --dry-run                      Print the SQL that would run instead of running it
      --allow-non-empty              Run every script on a database that has tables but no history (normally refused)
      --rerun-repeatables            Also re-run repeatable scripts that have not changed
```

### check

Pre-deploy checks: drift, what the pending scripts change, and the dry-run script. With no flags, runs all three. Exits 13 when drift is found.

```
Usage: liftoff check [OPTIONS]

Options:
      --drift                        Compare the environment with what its applied scripts build
      --changes                      What the pending scripts will change
      --dry-run                      The SQL that would run
      --scratch <SCRATCH>            Scratch environment rebuilt for the comparison (default: the first with role "scratch")
      --report <FILE>                Also write a self-contained HTML report to this file
      --model                        Instead: fail (exit 14) when the schema model has changes no migration script makes; for pull requests
```

### validate

Check applied scripts against the files: failures, edits, missing files, out-of-order scripts

```
Usage: liftoff validate [OPTIONS]
```

### repair

Remove failed runs, accept edited scripts, forget scripts whose files were deleted

```
Usage: liftoff repair [OPTIONS]
```

### undo

Undo the latest applied migration with its U script

```
Usage: liftoff undo [OPTIONS]
```

### mark-applied

Record a pending script as applied without running it (the dev database it was written from)

```
Usage: liftoff mark-applied [OPTIONS] <SCRIPT>

Arguments:
  <SCRIPT>  File name in the migrations folder, e.g. V3__add_customers.sql
```

### baseline

Mark an existing database as already at a version, so older scripts never run there

```
Usage: liftoff baseline [OPTIONS]

Options:
      --version <VERSION>            The version the database is at [default: 1]
      --description <DESCRIPTION>    A note for the history table [default: baseline]
```

### clean

Erase every object in the project's schemas (only where allow_clean = true, or a scratch database)

```
Usage: liftoff clean [OPTIONS]
```

## Existing databases and baselines

### adopt

Start from an existing database: capture its objects as B0001 and record that it has them (checked on the scratch database first). For a project without scripts

```
Usage: liftoff adopt [OPTIONS]

Options:
      --description <DESCRIPTION>    Description in the file name [default: existing schema]
      --scratch <SCRATCH>            Scratch environment to check the capture on (default: the one with role "scratch")
```

### squash

Squash the versioned scripts into one baseline script (B…) that empty databases start from

```
Usage: liftoff squash [OPTIONS]

Options:
      --up-to <UP-TO>                Last version to include (default: all of them)
      --description <DESCRIPTION>    Description in the file name [default: squashed]
      --scratch <SCRATCH>            Scratch environment to build in (default: the first with role "scratch")
      --dry-run                      Print the script instead of writing it
```

### rebaseline

Replace the versioned scripts with one baseline script (checked to build the same schema), and take the old scripts out of the migrations folder

```
Usage: liftoff rebaseline [OPTIONS]

Options:
      --up-to <UP-TO>                Last version to fold in (default: all of them)
      --description <DESCRIPTION>    Description in the file name [default: baseline]
      --scratch <SCRATCH>            Scratch environment to build and check it in (default: the first with role "scratch")
      --archive <FOLDER>             Move the old scripts to this folder instead of deleting them (deleting needs them committed to git)
      --restart                      Start the numbering again: B0001 replaces every script; databases that ran them are checked against it on their next migrate
```

## Compare

### compare

Compare the schema of any two sides; then save the differences as a script, write them as the next migration, or apply them. A side is an environment, a database URL, model, migrations, or a snapshot file (.json)

```
Usage: liftoff compare [OPTIONS]

Options:
      --source <SIDE>                What it should look like (e.g. dev, model, snapshot:prod.json)
      --target <SIDE>                What gets changed to look like the source (e.g. test, a URL, migrations)
      --scratch <SCRATCH>            Scratch environment, when a side is model or migrations (default: the one with role "scratch")
      --object <ID>                  Only this difference, by its id as listed (e.g. table:public.orders); repeatable
      --script <FILE>                Write a script that makes the target like the source to this file (- to print it)
      --migration <DESCRIPTION>      Write the differences as the next migration, with this description
      --undo                         With --migration: also write the undo script
      --apply                        Run the differences on the target database now (outside its migration history)
      --confirm-production           Needed with --apply when the target is a production environment
```

### snapshot

Save the schema of a side to a file, to compare with later without a connection (liftoff compare --source snapshot:FILE …)

```
Usage: liftoff snapshot [OPTIONS]

Options:
      --of <SIDE>                    What to save: an environment, a database URL, model or migrations
      --out <FILE>                   The file to write (default: snapshots/<side>-<date>.json)
      --scratch <SCRATCH>            Scratch environment, for model or migrations
```

### data-compare

Compare the rows of the tables two databases share (by key), fast on big tables; then show the differing rows, write a sync script, or apply it

```
Usage: liftoff data-compare [OPTIONS]

Options:
      --source <SIDE>                The database whose rows are right: an environment or a URL
      --target <SIDE>                The database to compare (and change): an environment or a URL
      --table <TABLE>                Only this table, as schema.name (repeatable)
      --rows <TABLE>                 Also show the differing rows of this table
      --kind <KIND>                  With --rows: only_in_source, only_in_target or different [default: different]
      --offset <OFFSET>              With --rows: skip this many [default: 0]
      --limit <LIMIT>                With --rows: show this many [default: 50]
      --script <FILE>                Write the INSERT/UPDATE/DELETE statements that make the target match to this file (- to print them)
      --apply                        Run those statements on the target, in one transaction
      --confirm-production           Needed with --apply when the target is a production environment
      --no-insert                    Leave out rows only in the source
      --no-update                    Leave out rows that differ
      --no-delete                    Leave out rows only in the target
      --save-diff <FILE>             Also save the differing keys to this file, for --from-diff
      --from-diff <FILE>             Compare nothing: use the differences saved with --save-diff (for --rows, --script, --apply)
```

## Teams and pipelines

### renumber

Move the migration scripts this branch adds after everything on another branch (e.g. origin/main), with their undo scripts; with --check, only say which are not

```
Usage: liftoff renumber [OPTIONS]

Options:
      --after <REF>                  The branch the new scripts must come after, e.g. origin/main
      --check                        Change nothing; fail (exit 12) when a new script is not numbered after REF
```

### ci

Write a CI workflow that runs the migrations

```
Usage: liftoff ci [OPTIONS]

Options:
      --stage <STAGE>                Environments to deploy to, in order (repeat the flag; required)
      --branch <BRANCH>              The branch whose pushes deploy [default: main]
      --no-checks                    Leave out validate and the drift check
      --model <MODEL>                Pull requests and the schema model: off, check (fail when a model change has no migration script) or generate (write it and commit it to the pull request) [default: off]
      --install <INSTALL>            Command that installs liftoff on the runner [default: curl -fsSL -o liftoff https://github.com/sanderstad/liftoff/releases/latest/download/liftoff-linux-x64 && sudo install -m 755 liftoff /usr/local/bin/liftoff]
      --write                        Write .github/workflows/liftoff.yml (otherwise print it)
      --force                        Replace an existing workflow file
```

## Flyway

### import-flyway-history

Copy an environment's Flyway history into LiftOff's history table, once

```
Usage: liftoff import-flyway-history [OPTIONS]

Options:
      --table <TABLE>                Flyway's history table [default: flyway_schema_history]
      --accept-edited                Import even if applied scripts changed since they ran (stores the current files' checksums)
```
