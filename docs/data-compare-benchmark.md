# Data compare benchmark

How fast `liftoff data-compare` is on SQL Server and PostgreSQL, by table size and by how much of
the table differs, for a table with a primary key and for a heap (a table without a key, compared
as whole rows). Measured on 2026-10-12. All 168 results found exactly the differences that were
made, and every sync left both sides the same (0 wrong). Tables of 1, 2 and 5 million rows are
further down: [1, 2 and 5 million rows](#1-2-and-5-million-rows).

## At a glance

Times in seconds (median of 3 runs) for a 300,000-row table.

| 300,000 rows | changed | SQL Server: compare / script / apply | PostgreSQL: compare / script / apply |
| --- | ---: | --- | --- |
| with a key | 1% | 4.94 / 0.11 / 0.38 s | 2.26 / 0.02 / 0.29 s |
| with a key | 5% | 5.17 / 0.57 / 1.62 s | 2.35 / 0.11 / 1.22 s |
| with a key | 10% | 5.19 / 1.14 / 3.43 s | 2.22 / 0.21 / 2.43 s |
| with a key | 20% | 5.94 / 2.33 / 7.24 s | 2.15 / 0.32 / 4.99 s |
| heap (no key) | 1% | 5.38 / 1.41 / 3.19 s | 2.92 / 1.33 / 2.39 s |
| heap (no key) | 5% | 4.58 / 2.11 / 6.04 s | 2.68 / 1.25 / 2.84 s |
| heap (no key) | 10% | 6.31 / 4.03 / 9.86 s | 2.70 / 1.34 / 3.58 s |
| heap (no key) | 20% | 5.84 / 9.95 / 21.11 s | 2.67 / 1.66 / 6.99 s |

- **Comparing scales with the table, not with the number of differences.** With a key, SQL Server
  takes about 5–6 s and PostgreSQL about 2 s for 300,000 rows, whether 1% or 20% of the rows differ.
- **With a key, script and apply grow with the differences only.** The rows are found by their key,
  so 60,000 differences in a 300,000-row table take 2.3 s to script and 7.2 s to apply on SQL Server,
  0.3 s and 5.0 s on PostgreSQL.
- **A heap costs more.** Without a key a changed row is a delete plus an insert, so a heap has twice
  the differences to sync, and its rows can only be found by reading the table and hashing every
  row. LiftOff does that once per 50,000 rows it reads and once per 10,000 rows it deletes. At
  300,000 rows and 20% different: 21 s to apply on SQL Server, 7 s on PostgreSQL.
- **PostgreSQL is about twice as fast** on the same machine for the same work.

## What was measured

- **Machine:** AMD Ryzen 7 5800X (8 cores, 16 threads), 64 GB, Windows 11; both databases in local
  containers (Rancher Desktop), with nothing else running against them.
- **Databases:** SQL Server 2022 Developer (CU21), PostgreSQL 16.15; LiftOff 0.1.0 on Node 24.
- **Tables:** six columns (`id bigint`, `account int`, `kind`, `amount decimal(12,2)`, `at`
  timestamp, `note` text, one in nine NULL), filled with 100 to 300,000 rows. `keyed` has `id` as
  its primary key; `heap` has the same columns and rows and no key.
- **Changes:** in the target, 1%, 5%, 10% or 20% of the rows, spread over the whole table
  (`(id * 7919) % 10000`): one third changed (`amount` and `note`), one third deleted, and as many
  extra rows added. Both tables get exactly the same changes.
- **Columns:**
  - *found*: what data compare reported; checked against the changes made. With a key: deleted rows
    are only in the source, added rows only in the target, changed rows changed. In a heap a
    changed row is one only in the source and one only in the target.
  - *compare*: connecting to both databases and comparing (`DataSession.open`).
  - *script*: writing the INSERT / UPDATE / DELETE script that makes the target match.
  - *apply*: writing and running that script on the target, in one transaction.
  - *compare again*: comparing after the sync; every run found no differences left.
  - Compare and script are the median of 3 runs, with the fastest and slowest in brackets; the
    first run of each includes opening the connections. Apply and compare again ran once.
- **Heaps, before and now:** the heap tables show the times before and after three changes made
  during this benchmark: rows are read by their hash 50,000 at a time instead of 1,000, extra rows
  are deleted 10,000 per statement instead of 1,000, and on SQL Server that delete reads its list of
  rows once (a hash join) instead of once per row.
- **To run it again:** in `packages/liftoff`, with `LIFTOFF_TEST_MSSQL` or `LIFTOFF_TEST_PG` set,
  `node scripts/bench-datacompare-matrix.ts ms 100,1000,10000,50000,100000,200000,300000 1,5,10,20 3`
  (or `pg …`). It drops and creates the databases `bench_a` and `bench_b`.

## 1, 2 and 5 million rows

The same measurement on bigger tables: 48 more results, all of which found exactly
the differences that were made and left both sides the same after the sync (0 wrong). Nothing ran
out of memory.

These ran with two changes made after the first part of this benchmark, so their compare times
are not directly comparable with the tables above:

- **Smaller buckets, read in chunks.** Rows are grouped into buckets of about 16 instead of 250,
  and the key and hash pairs of differing buckets are read 500,000 rows at a time. With changes
  spread over a table, almost every 250-row bucket differed, so nearly every pair had to be read:
  1,000,000 rows with 1% changed took 17.5 s to compare on SQL Server and 1 GB of memory, now
  5.5 s and under 400 MB.
- **PostgreSQL matches the differing buckets as a set.** With 16-row buckets their list grew to
  tens of thousands, and PostgreSQL checked that list element by element for every row: a
  first run took 55 s for 1,000,000 rows with 5% changed and 162 s for 2,000,000. Matching it as
  a set brought those to 5.5 s and 9.1 s.

- **Compare grows with the table and, less, with the changes.** On PostgreSQL a keyed table of
  5,000,000 rows compares in about 12 s with 1% changed; on SQL Server in about 20 s.
- **Script and apply grow with the differences**, as on smaller tables.
- **Heaps cost the most at this size**: at 20% changed, 667,000 rows have to be deleted and
  667,000 inserted, each found by hashing every row: about 13 minutes to apply on either database.
  Give big tables a primary key.
- The SQL Server run at 5,000,000 rows, 20% changed, with a key, shares the machine with a short
  test in two of its three compares, which shows in its wide range (60–95 s).

## Reading the numbers

- Below about 10,000 rows everything takes well under a second; the time is mostly connecting.
- SQL Server's compare times at 50,000–300,000 rows depend on it running the hashing on all cores.
  LiftOff asks for a parallel plan where the server allows it; a server that does not, or a busy
  one, will be slower.
- These are local containers with no other load. A shared server, a network between LiftOff and
  the database, or wider rows make every step slower, but the shape stays the same: compare grows
  with the table, script and apply with the differences, heaps cost more than keyed tables.
